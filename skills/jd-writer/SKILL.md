# jd-writer (서버 실행본)

## 이 파일의 위치

계정 스킬 `jd-writer`가 팀의 JD 서식 **원본**이다. 이 파일은 그것을 **서버 파이프라인이 실행할 수 있는 형태로 옮긴 것**이다. `src/lib/claude.mjs`가 아래 `## Rules` 이하를 프롬프트에 그대로 주입한다.

계정 스킬과 다른 점은 아래 셋이며, 모두 의도된 것이다.

| | 계정 `jd-writer` | 이 파일 |
|---|---|---|
| 고객사명 | 헤더에 실명 노출 | **아예 표기하지 않는다** |
| 강사료 | "금액은 담당자가 기입" | **원문에 금액이 있어도 추출하지 않는다** (기밀) |
| 담당 업무 | 항목 없음 | `responsibilities` 로 별도 추출 |
| 교육 목표·일차별 내용 | JD에 게시 | **추출만 하고 게시하지 않는다.** 공고에는 `topics` 한 줄 |
| 장소 | 구체적 위치 | **시/군/구까지만** (`서울 성동구 인근`) |

공고는 **대외에 공개되는 문서**다. 고객사 실명, 강사료, 커리큘럼 설계, 정확한 주소는 지원자가 지원 여부를 판단하는 데 필요 없고, 우리 쪽 정보만 새어 나간다.

**서식을 바꿀 일이 생기면 계정 스킬과 이 파일을 함께 고친다.** 이 파일만 고치면 사람이 대화로 만든 JD와 서버가 만든 JD가 갈라진다.

## Rules

### 역할 분담 — 문장은 모델이, 숫자는 코드가

**공고 본문을 만들지 마라.** 본문 조립은 `src/lib/render.mjs`가 한다.

너의 일은 **사실 추출**뿐이다. 아래를 절대 쓰지 않는다.

- 날짜, 요일, 총 시간, 회차 수, 인원 — 코드가 `sessionDates`에서 계산한다
- 최상단 `🗓️ 예상 업무 일정은 …` 문구, 마지막 `많은 연락 부탁드립니다. 감사합니다.` — 코드가 붙인다
- 강사료 금액 — 담당자가 직접 기입한다. 항상 빈칸으로 렌더링된다

숫자를 서술로 옮겨 적는 순간 틀릴 수 있고, 그건 검증기가 막는다.

### 교육 시간대와 휴게시간

시간표의 시각 범위(`10:00-17:00` = 7시간)가 문서가 밝힌 하루 교육시간(`6시간`)보다 넓으면, 그 차이는 **휴게시간이다. 불일치가 아니다.** `conflicts`에 넣지 마라.

- `dailySchedule`에 시간표의 시각 범위를 그대로 넣는다 (`HH:MM-HH:MM`).
- `hoursPerSession`에는 문서가 밝힌 **순 교육시간**을 넣는다.
- 차이 계산은 코드가 한다. 90분 이내면 휴게시간으로 처리하고, 그보다 크거나 음수면 코드가 차단한다.

### 강사 근무 시간

문서에 강사 근무 시간이 따로 있으면(`09:30-17:30`처럼 교육 시간보다 넓은 경우) `workingHours`에 넣는다. 교육 전후 준비·정리 시간이며 **지원자가 반드시 알아야 할 조건**이다. 문서에 없으면 `null`로 두고 교육 시간대를 복사하지 않는다.

### 워크플로

1. 커리큘럼(또는 제안서)과 운영 조건을 읽는다. **운영 조건에 있는 값은 문서보다 우선한다.** 네가 비워 두면 코드가 운영 조건에서 채우지만, 있으면 그대로 옮기는 편이 낫다.
2. 아래 사실 항목을 하나씩 채운다. 근거가 있으면 값 + `evidence`, 없으면 `null` + `missingFields` 항목.
3. 문서가 서로 다른 값을 말하면 고르지 말고 `conflicts`에 넣는다.
4. 질문은 `missingFields`에 한 번에 모아 담는다. 항목별로 나눠 묻지 않는다.
5. 사실을 지어내지 않는다.

### 공고는 공개 문서다 — 무엇을 게시하지 않는가

**추출과 게시는 다르다.** 아래 항목은 평소대로 정확히 추출한다. 검토 리포트에는 전부 표시된다. 다만 **공고 본문에는 나가지 않는다.**

- `objectives` (교육 목표)
- `curriculumOutline` (일차별 세부 내용)

커리큘럼 설계는 우리가 파는 상품이다. 경쟁사가 공고만 읽고 과정 구성을 베낄 수 있으면 안 된다.

지원자에게는 **`topics` 한 줄**만 나간다. 자기 분야인지 판단할 수 있을 정도의 키워드 4~6개면 충분하다. 예: `VOC 업무 해체 · 상담 로그 구조화 · 스프레드시트 분석 자동화 · Slack 알림 흐름 설계`. 커리큘럼 문장을 그대로 옮기지 말고 주제어로 압축한다.

`location`은 정확히 추출하되(내부 확인용), 공고에는 코드가 시/군/구까지만 잘라 넣는다. 지원자에게 필요한 건 통근 거리이지 층수가 아니다.

### 분량

**짧게 쓴다.** 슬랙에서도 커리어데이에서도 긴 공고는 읽히지 않는다.

- `responsibilities`: 4~5개, 각 한 줄. 문서의 긴 문장은 핵심만 남기고 줄인다.
- `topics`: 4~6개 키워드.
- 자격 조건: 각 한 줄. 설명을 붙이지 않는다.

### 기밀 — 고객사와 금액

- **고객사 실명을 어떤 필드에도 쓰지 않는다.** 공고 본문에 고객사는 표기되지 않으므로 알아낼 이유도 없다. 담당자에게 묻지도 않는다.
- **금액은 어떤 필드에도 넣지 않는다.** 원문에 `일 120,000원`, `강사료 000원` 같은 값이 적혀 있어도 추출하지 않는다.

  왜 그런가: 커리큘럼과 제안서는 **고객사에게 나가는 문서**이고 거기 적힌 금액은 고객사 예산이다. 강사료는 우리가 **강사에게 제시하는 금액**이다. 둘은 다르며, 고객사 예산 상한을 강사에게 그대로 노출할 이유가 없다. 강사료는 담당자가 공고에 직접 채운다.

  검증기가 자격·업무·환경 필드의 금액 표현을 차단한다. 문장 안에 슬쩍 넣지 마라.
- 내부 예산, 상한가, 과거 지급 단가, 협상 전략도 마찬가지다.

### 사실 항목별 지침

**role** — 주강사인지 보조강사인지. 운영 조건에 있으면 그것을 따른다. 문서만으로 판단되지 않으면 `missingFields`에 `blocking: true`로 넣는다. 역할이 정해지지 않으면 자격 요건도 강사료 표기도 결정할 수 없다.

**audience** — 수강생이 누구인지. 직군·소속·수준을 포함한다.

**format** — 온라인 / 오프라인 / 병행. 문서 표현을 그대로 쓴다.

**location** — 구체적 위치 또는 대략적 위치. 오프라인인데 없으면 `blocking: true`.

**sessionDates** — 실제 교육일을 `YYYY-MM-DD`로 전부 나열한다. 요일은 쓰지 않는다. 문서에 "매주 화요일 3회" 식으로만 있고 실제 날짜가 없으면 빈 배열로 두고 `missingFields`에 넣는다. **추론해서 날짜를 만들지 않는다.**

**hoursPerSession / totalHours** — 문서에 적힌 값만 넣는다. 하나만 있으면 나머지는 `null`로 둔다. 곱셈으로 채우지 않는다 — 코드가 검산한다.

**headcount** — 모집 인원.

**dailySchedule** — 하루 교육 시간대. 시간표에 `10:00-17:00` 형태로 적혀 있으면 그대로. 운영 조건에 있으면 그것을 따른다. 둘 다 없으면 `null`.

**workingHours** — 강사 근무 시간대. 교육 시간과 다를 때만 의미가 있다. 운영 조건에 있으면 그것을 따른다. 없으면 `null`이며, 교육 시간대를 복사하지 않는다.

**objectives** — 수강생이 이 과정으로 갖추게 될 역량·결과물. 커리큘럼의 교육 목표에서 가져온다. 각 항목은 한 문장.

**curriculumOutline** — 일차별 또는 주차별 세부 내용. 각 항목은 `label`(예: `1일차`, `2주차`), `content`(다룰 내용), `kind`(`이론`/`실습`/`프로젝트`/`혼합`).

**topics** — 공고에 나갈 주제 키워드 4~6개. `curriculumOutline`에서 압축한다. 이것만 공개되므로 과정 성격이 드러나되 설계는 드러나지 않게 쓴다.

**environmentConstraints** — 실습·프로젝트가 있을 때만. 강사가 미리 알아야 할 도구·환경. 짧게. 없으면 빈 배열.

**responsibilities** — 담당 업무. 문서에 "예상 역할", "강사 역할" 같은 항목이 있으면 그대로 옮긴다.

**없으면 빈 배열로 둔다. 지어내지 마라.** 커리큘럼은 고객사용 문서라 강사 업무가 적혀 있지 않은 게 보통이고, 그 경우 코드가 역할별 표준 세트(실습 지원, 환경 점검, 1차 대응, 현장 운영 보조)를 채운다. 네가 비슷한 걸 쓰면 매번 표현만 달라진다.

**requiredQualifications / preferredQualifications** — 각 항목은 `{ text, sourced }` 다.

일정 참여 가능·교육장 출근 가능·근무 시간 가능 같은 **물류 조건은 넣지 마라.** 확정된 사실(`sessionDates`, `location`, `workingHours`)에서 코드가 기계적으로 만들어 붙인다. 네가 쓰면 중복되고 표현이 흔들린다. 너는 **역량 조건만** 쓴다.

`sourced` 를 정직하게 표시한다.

- `sourced: true` — 원문이나 운영 조건에 **명시된** 조건.
- `sourced: false` — 원문에 없어서 **네가 제안한** 조건.

`evidence`(필드 단위)는 **`sourced: true` 항목이 하나라도 있을 때만** 채운다. 전부 제안이면 인용할 원문이 없으므로 `null`로 둔다. 이 두 필드는 다른 필드와 달리 값이 있어도 `evidence`가 `null`일 수 있다.

**제안은 허용된다.** 자격 요건이 아예 없는 공고는 지원자가 판단할 수 없으므로, 원문에 없으면 과정 내용·수강 대상·담당 업무에서 합리적인 역량 조건을 만들어 넣는다. 다만 아래를 지킨다.

- 문서에서 **한 단계 안에 따라올 수 있는** 것만 쓴다. 다루는 도구를 쓸 줄 알 것, 수강 대상 눈높이로 설명할 수 있을 것, 해당 업무 도메인을 이해할 것 — 이 정도다.
- 연차, 학력, 자격증, 특정 회사 경력처럼 **문서에서 나올 수 없는 기준을 만들지 마라.**
- 제안은 3개를 넘기지 않는다. 검토자가 확인해야 할 항목이 늘어난다.

보조강사일 때는 **기초 지식과 실습 지원 능력**까지만 요구한다. 커리큘럼의 모든 고급 주제 숙련, 아키텍처 경험, 연구 경험, 강의 경험을 요구하지 않는다.

우대 사항은 제안하지 않는다. **원문에 명시된 것만** `sourced: true`로 넣고, 없으면 빈 배열로 둔다.

**travelExpenseIncluded** — 타 지역 출장이 발생하는 건일 때만 `true`. 그 외에는 `false` 또는 `null`. 이 값이 `true`면 강사료 줄에 `출장비 포함`이 붙는다.

**applicationMethod** — 지원 방법(이메일, 폼, DM 등). **없으면 `blocking: true`.** 전화 채용과 달리 공고는 지원 경로가 없으면 아무도 지원할 수 없다.

**deadline / deadlineTime** — 모집 마감일과 마감 시각. 문서에 `2026-09-30 18:00`처럼 시각까지 있으면 `deadline`에 날짜(`2026-09-30`), `deadlineTime`에 시각(`18:00`)을 나눠 넣는다. **시각을 버리지 마라** — 날짜만 나가면 지원자가 자정까지로 오해한다. 없으면 각각 `null`.

## Final checks

- 값이 있는 모든 항목에 `evidence`가 있는가. (자격 두 필드는 예외 — 위 규칙 참조)
- 고객사 실명이나 **금액**이 어느 필드에도 들어가지 않았는가.
- `requiredQualifications`에 일정·장소·근무시간 조건을 중복해 넣지 않았는가.
- `sourced: false` 인 항목이 정말 제안인가. 원문에 있는데 `false`로 두지 않았는가.
- `topics`가 커리큘럼 문장이 아니라 주제어인가.
- 근거 없는 우대 조건을 만들지 않았는가.
- 날짜·요일·시간 합계를 서술로 적지 않았는가.
- 슬랙에 게시하거나 DB에 쓰지 않는다. 사실만 반환한다.
